The details that change how you debug

  1. A stage can be complete while downstream work is missing. Check actual output, receipt and consumer activity—not just the producer's state.
  2. A tracking row is not a broker receipt. The common sender distinguishes uncertain from confirmed sends, but some caller guards use weaker tests. Those are source-inferred failure windows, not reproduced incidents.
  3. AIQ L1 and entity classification can overlap. Entities are sent before global-category work finishes; the graph is not strictly one service at a time.
  4. Duplicate content is not always terminal. A new account can link to existing article content and continue. Same-account prior uploads take the terminal duplicate-document path.
  5. FAILED, COMPLETED, SKIPPED, READY and DUPLICATE belong to different state models. Activity completion is not the same as document readiness or complete enrichment.
  6. A crash may follow a successful database commit. Synthesis recovery reads committed Accelerate evidence before deciding to repeat work.

1. The identities to keep separate

Imagine a fictional news page, “Example Components opens a factory,” discovered on a fictional feed.

F = feed UUID, e.g. 11111111-1111-4111-8111-111111111111.
W1 = one web-extraction L1 activity, not the article.
W2 = the L2 activity for this article URL.
A = article UUID, created only after content persistence selects the nonduplicate path.
Q1 = AIQ L1 activity; E1 = entity-classification activity; Q2 = AIQ L2 activity; T1 = model-tagging activity.
D = Accelerate integer document ID, e.g. 900001, created downstream for a crawl.
M = one msg_tracking_id. Every handoff has its own M.
C = continuity_id shared for correlation across this item's messages, not a unique message key.

The sender's activity ID becomes the next message's source_activity_id. It does not become the receiver's activity ID. The receive path registers or recovers that receiver activity. For example Q1 is carried as source_activity_id in the EC message; E1 is the EC row that consumes it.

BaseMsg declares msg_tracking_id and continuity_id. Typed messages add article/feed/document identifiers and often an activity_trail dictionary. Queue request type and destination layer are routing metadata, not substitutes for those IDs.

2. Crawl step 1: the feed scheduler produces work, not an article

FeedService.layer_one_pipeline selects ACTIVE non-manual feeds whose next_run_at is due, excluding those with recent queued/processing L1 work. 3. Crawl step 2: Web Extraction L1 filters the list before article work

WebExtractionService.layer_one_pipeline:
1. Loads blacklist state before saving a new feed fingerprint. Otherwise a failed blacklist read could save the hash, and the retry could call the feed unchanged.
2. Fetches an article list.
3. check_feed_content_changed updates fingerprint/adaptive state. An unchanged feed marks W1 SKIPPED with UNCHANGED_FEED_CONTENT and exits.
4. Persists the list response.
5. Normalizes URLs; removes recently processed URLs and URLs over the failed-attempt cap.
6. Removes URLs already sent by this W1 on an earlier attempt.
7. Filters blocked domains, publication dates and maximum count. Per-feed max_articles overrides the default.
8. Sends one WebExtractionLayerTwoMsg per remaining URL.

The L2 message carries F, article_url, source_activity_id=W1 and activity_trail. If no URL remains, W1 becomes COMPLETED even though no article proceeds. If the batch partly fails, the source logs failed versus successful sends and ultimately completes W1; “L1 complete” therefore does not mean every candidate became a document.

Read/write surface:
- feeds.feeds and web_extraction.feed_hashes/scheduling-related state.
- web_extraction.responses for the fetched list.
- Existing activity/status/queue-tracking records for URL and resend filtering.
- web_extraction.sent_sqs_messages for the L2 batch.

4. Crawl step 3: Web Extraction L2 is a gated state machine

process_layer_two_msg validates article_url, uses a pinned database connection, marks W2 PROCESSING and takes a URL-derived advisory lock. The lock survives intermediate commits; it is not a database transaction held open across network calls. Two activities for the same URL may both be PROCESSING while one waits for the lock.

The core layer_two_pipeline has these meaningful branches:

A. Early media-container gate. A new unsuitable URL can be skipped before fetch/LLM/embedding costs. If an earlier attempt has already persisted an outcome, the gate defers to recovery rather than abandoning it.

B. Existing response. Rebuild the article from web_extraction.responses and reuse its created_at as scrape time. Recover frozen similarity time/group context. Site-error and paywall guards still run. A prior completed article/outcome can be recovered and forwarded without re-fetching or reclassifying it.

C. Fresh response. Check domain blacklist and feed status, fetch article, reject site-error/paywall content before writing a response, then persist the usable response.

D. Landing-page gate, content normalization and publication-date validation. Rich markdown is for stored/displayed content; plain stripped text is used for embeddings and dedup. A trustworthy date is resolved and stale content can be skipped. This prevents formatted image blocks/boilerplate from silently changing the embedding basis.

E. Embedding and source classification. classify_layer_two_article combines similarity, optional verifier decisions, retry recovery and grouping policy:
- DUPLICATE: write/upsert web_extraction.duplicated_articles, retain the matched canonical article ID, record activity_article_statuses, end W2 as DUPLICATE; no new AIQ/translation handoff.
- Nonduplicate: write/reuse web_extraction.articles, zyte_articles and article_chunks. Both unique and syndicated outcomes have a source_classifications/group relationship. A syndicated article is still its own stored article; it is not the same as a discarded duplicate.

F. Record activity_article_statuses before sending. Then decide translation from the article's text. An English/no-translation path sends AIQuestionnaireLayerOneMsg directly with A, F, source_activity_id=W2 and source_microservice=WEB_EXTRACTION. Otherwise it sends ArticleTranslationLayerOneMsg, including A, F, URL and webex_layer_two_activity_id=W2.

G. Start the image-processing work for the nonduplicate and mark W2 COMPLETED. The image result is separate from whether the text handoff was already sent.

6. AIQ L1: entity extraction is its own persisted result

AIQuestionnaireService.ai_questionnaire_layer_one_pipeline first reads the correct article text and calls run_entities_layer_one. That helper loads versioned prompts, performs PEOPLE, ORGANIZATIONS and LOCATIONS extraction, and writes three ai_questionnaire.entity_responses rows transactionally. A row records A, Q1, entity_type, model and prompt-version provenance, raw response and validated response.

Retry behavior is explicit:
- All three rows and sent EC message exist: skip this step.
- Three rows exist, message absent: resend only.
- Partial row set: log the anomaly, rerun the calls; ON CONFLICT DO NOTHING preserves already-written rows.

Important qualification: the current 'message sent' caller guard checks tracking-row existence, not confirmed broker receipt. The retry bullets above describe the branch intent; an UNKNOWN/failed send can still be skipped by that guard. See queue-delivery-detail.txt section7 for the source-inferred window.

The EC payload is EntityClassificationLayerOneMsg(A,F,article_type,source_activity_id=Q1,manual_upload_account_id?,doc_id?,activity_trail,source_microservice). It is sent BEFORE the separate L1 global-category work. That means EC can run while Q1 continues its global prompts. This is not a strictly serial “finish all L1 work, then EC” pipeline.

Global L1 categories write ai_questionnaire.model_category_responses. The current entity path reads entity_responses, not “latest category JSON” from that older table. Empty global categories can finish Q1 after the entity handoff already happened.

7. Entity Classification: turn mentions into defensible account relevance

EntityClassificationService.entity_classification_layer_one_pipeline receives Q1 as source_activity_id. get_entities_response selects every entity type with BOTH article_id=A and layer_one_activity_id=Q1. Missing one of the three rows raises; it does not mix the newest people from one run with organizations from another.

The core matching phase:
- Normalize/merge repeated entity names and evidence.
- Query master_text -> active text_match_xref -> nvw_match entities, with category priority. SQL normalizes the stored names consistently.
- Resolve source-map/context metadata and corporation/industry provenance.
- Write EC people, organizations, locations, matched_entities, industries and article_entity_map rows.
- For MVW feeds, read enabled feed_markets for baseline market relevance.
- Write per-organization context and candidate_observations for unmatched organizations under fail-safe savepoints.

These IDs are not interchangeable. A master nvw_match entity integer, a corporation ID and an Accelerate canonical platform_entity UUID serve different roles. Industry references can numerically collide with corporation IDs; existence of the integer alone is not a valid classification rule.

Crawled-document projection:
- Build DocEntityReason records explaining corporation, market or industry relevance.
- With no reasons, return no document, skip Q2 handoff, and still complete E1.
- Otherwise create/reuse doc.doc_content and doc.documents, write doc.doc_entity_map, copy embeddings to ai.document_chunks and write entity lists to doc.source_data.
- Return D, record entity_classification.doc_article_map(A,D,E1), then send AIQuestionnaireLayerTwoMsg(A,F,document_id=D,source_activity_id=E1,account_types,...).

The mapping deliberately contains a UUID article and an integer external doc_id. It has a unique (article_id,doc_id,layer_one_activity_id) constraint. There is no cross-database foreign key on doc_id; correctness depends on the explicit write/recovery contract.

8. AIQ L2 and tagging: classification work is not the final status

Q2 selects global and account-type-specific categories, resolves versioned prompts/schemas, reads its own prior filter results for retry skipping, and gets the correct article text. Global and account category work run concurrently. Completed per-account results are batch-written to ai_questionnaire.filter_model_responses; global results also use that table.

When at least one per-account category succeeds, or there were no per-account categories:
- Collect successful/skipped-existing category IDs plus global IDs.
- If that list is nonempty, send ONE AIModelTaggingLayerOneMsg with A,F,doc_id=D,source_activity_id=Q2,category_ids.
- Mark Q2 COMPLETED.

If every required per-account category fails, Q2 is marked FAILED and raises. If the combined applicable list is truly empty, no tagging message is sent even though Q2 completes. That is a different case from all model calls failing.

Model tagging:
- Validate that (A,D) has a doc_article_map row.
- Resolve category IDs against the current active registry; refresh/recheck before declaring unknown.
- Fetch FilterModelResponse rows scoped to Q2, not merely A.
- Use the keys actually emitted in each validated response, not a newly reloaded category schema.
- True matches create category_prompt_version_runs and data_model_responses.
- False matches do not create those rows; they can downgrade previously true document/model associations.
- After DataLake commit, upsert Accelerate ai.doc_ai_model_map; consolidate false downgrades without clearing a model that is true in another category.
- Set doc.documents.status=READY; then mark T1 COMPLETED.

No new free-form LLM call is required in model tagging. Its job is projection/reconciliation of the already validated results. A missing FMR or unknown model/category may be logged and skipped, yet the final document can still become READY. READY is therefore not evidence that every conceivable category produced a tag.

9. Manual upload: same downstream machinery, different identity and branches

Start with a fictional account 7001 and pre-created Accelerate document D=900101. The incoming ManualUploadMsg contains account_id, doc_id and the stored-object reference. W3 is a new web-extraction layer-three activity. No real object keys are used in this report.

manual_upload_pipeline first marks D PROCESSING. It checks existing activity_article_statuses and ManualUploadAccount recovery anchors BEFORE loading/embedding. That avoids matching a retry against its own previously committed article chunks.

It reads the upload once to obtain rich stored text, plain embedding text and image ordinals. Oversized objects, PDF processing/conversion limits and textless documents are terminal extraction failures; transient object reads propagate for retry. Nonempty plain text is embedded and compared to the content corpus.

The branching is more subtle than “duplicate means stop”:
A. No duplicate: atomically create Article + ManualUpload + ArticleChunks + ManualUploadAccount. Metadata enrichment follows.
B. Content matches a crawled article that has no ManualUpload yet: reuse A, create the manual-upload representation and account link, and CONTINUE.
C. Content matches a ManualUpload but this account has no ManualUploadAccount: create this account's link/document association and CONTINUE.
D. Content matches an article already uploaded by THIS account: write DuplicatedArticle and select the terminal duplicate path.

A/B/C send ArticleTranslationLayerOneMsg with A, the manual-upload feed ID, article_type=MANUAL_UPLOAD, manual_upload_account_id, the preexisting D, source_activity_id=W3 and webex_layer_three_activity_id=W3. The stored Article.feed_id can be the original crawl's feed when A is reused; it must not be assumed equal to the message's manual-upload feed.

In EC, the uploading account's view type is explicitly added to Q2 account_types even if master matching found no relevant entity. An MVW upload may seed its own account market for evidence. This account-type floor selects applicable categories; it is not a fabricated entity match.

EC reuses the pre-created D and intentionally skips doc_entity_map writes for manual uploads because account association already exists. On the first content attachment it sets QUESTIONING. On a reuse/retry mapping branch it still updates chunks/source_data/images but may skip that status reset. Tagging ultimately sets READY after successful processing.

10. Same-account duplicate: a different document, no EC pass

For branch D above, assume existing original document 900101 and a newly uploaded duplicate document 900102.

The service:
- Records the duplicate article outcome before cross-database projection.
- Links duplicate document 900102 to original 900101.
- Projects article images onto 900102.
- Copies the original's entity source_data rows (the allowed entity-model IDs only) onto 900102.
- Sets 900102 DUPLICATE.
- Marks W3 DUPLICATE.
- Sends no translation, AIQ or EC message.

The original and duplicate document IDs remain separate. Upsert keys include the destination doc_id, so the copy must not overwrite the original document's rows. A retry re-applies linkage/projections from the stored outcome.

Known timing limit: image projection has a bounded sentinel wait. source_data projection has no wait; if EC has not yet written original source_data, it copies zero rows and still ends duplicate. Nothing later automatically reprojects it. That is already marked DAT-8857 in source. A reader should not equate DUPLICATE with “all enrichment successfully copied.”

Manual L3 also does not participate in the L2 syndication-grouping policy. A SYNDICATION_CANDIDATE content outcome is treated as nonduplicate for this branch.

12. What to check when the fictional document “disappears”

  • No W2: was the feed unchanged, URL recent/already sent, failure-capped, blocked, old, or excluded by cap?
  • W2 but no A: did an early gate skip before persistence? A duplicate points at an existing A instead of creating one.
  • A but no D: did EC find no relevance reasons, or is matching/projection failed? For manual upload D already exists; look for its map and current status instead.
  • Q1 says FAILED while EC work exists: the entity handoff preceded later global prompt work.
  • E1 completed but no Q2: no document was returned; a completed EC activity alone is not a successful user-visible document.
  • Q2 completed but no T1: inspect the actual combined applicable category list; zero categories sends nothing.
  • T1 READY but a tag absent: inspect unknown-category, missing-FMR, unknown-model and false-result paths before blaming queue loss.
  • Duplicate D missing entity lists: check whether original source_data existed at projection time.
  • Repeated failed manual work still shows PROCESSING/QUESTIONING: cancellation/timeout paths differ from ordinary exceptions; this was researched for a separate proposal.

These are hypotheses grounded in branches, not claims any incident occurred today.

13. Current source versus misleading older descriptions

  • EC's current entity input is three run-scoped entity_responses, not the latest model_category_responses row.
  • Translation is conditional for crawled text; manual nonterminal uploads enter translation explicitly.

1. The identifiers answer different questions

- activity_id is the producing stage's run, passed into the helper and written to the layer-specific column of its sent_sqs_messages row.
- row.id is that database row's primary key, retained internally to update it later.
- msg_tracking_id is a UUID generated by the helper, injected into the payload and stored in the tracking row. It is the application message identity used at the next service, distinct from the SQS-assigned MessageId.
- native_sqs_message_id stores SQS's returned MessageId, parsed as a UUID, after the send succeeds.
- continuity_id is a cross-stage correlation identifier, not a unique delivery key.
Sources: H:110-135, :318-334, :397-408; src/common/models/contracts/sent_sqs_messages.py:19-47; src/common/aws/sqs/messages.py:9-20.

Receiver example: EntityClassificationLayerOneActivity has uniqueness on both msg_tracking_id and source_activity_id. Its msg_tracking_id references AIQ's sent_sqs_messages.msg_tracking_id. That foreign key explains why the upstream tracking row must already be committed before the receiver starts.

2. Single-message helper, in execution order

2a. Validate before doing DB or queue work.
_validate_send_inputs requires a valid SentSQSMessageBase subclass on client.tracking_table, supported destination request/layer combination and matching typed payload. Non-feed clients require activity_id. The actual exception is MessageRoutingException, despite older send helper docstring text mentioning ValueError.
Source: H:64-107.

2b. Prepare a provisional application message identity.
send_msg_to_target_queue generates uuid4(), mutates message_payload.msg_tracking_id, constructs a tracking row with request type, source layer and JSON payload, and attaches the layer-specific activity field.
Source: H:269, :313-334.

2c. Commit the tracking row before sending.
The helper owns a short-lived session; it accepts no caller session. It adds, flushes and explicitly commits the tracking row, then exits that session before invoking the SQS client. A failed write/commit raises DatabaseWriteException or DatabaseCommitException, and no send is attempted.
Source: H:277-288, :327-372, :377-383.
This protects downstream FK visibility for THIS tracking row. It does not automatically close an unrelated transaction a caller may have left open.

2d. Recover a conflicting insert, when the table enforces the relevant unique key.
If flush raises IntegrityError, _resolve_tracking_row_after_integrity_error rolls back and finds an existing row by the activity column associated with source_layer and the destination request_type. Missing activity information or no matching row produces DatabaseWriteException rather than pretending recovery succeeded.
Source: H:138-180, :191-207, :351-362.
It reuses the existing row PK and msg_tracking_id. The provisional UUID is replaced on the payload.
Source: H:209-236, :352-362.

2e. Decide whether a prior send is confirmed.
The helper skips the new send only when BOTH:
native_sqs_message_id IS NOT NULL
send_failed_at IS NULL
A row with neither marker is UNKNOWN, not successful; a row with a failure timestamp must be retried. On retry of a failure it clears send_failed_at and commits that change before the send.
Source: H:212-234.
If skip_send is true, it returns the existing msg_tracking_id without SQS I/O.
Source: H:374-375.

2f. Send after the tracking session exits.
The helper calls client.send_message using the current payload, destination layer and request type. A None response is converted into SQSException. Any ordinary Exception from the send phase triggers a best-effort failure stamp and is re-raised.
Source: H:377-395.
The failure stamp uses a separate session and an UPDATE by row PK; if the stamp itself fails, it reports a warning and preserves the original send exception.
Source: H:239-266.
CancelledError is not an ordinary Exception in the current Python runtime; a cancellation/process crash can therefore leave an UNKNOWN row without a failure stamp. The helper's retry predicate permits re-send of that UNKNOWN row if the caller reaches it.

2g. Record the native receipt, best effort.
A non-None response is treated as send success. The MessageId is parsed as a UUID and persisted in a new short transaction. Missing MessageId results in NULL; an invalid ID or DB update failure is logged, not raised. The function still returns msg_tracking_id.
Source: H:397-421.
Consequently helper return success and a later database receipt marker are not equivalent observations.

3. The transport inside client.send_message

C resolves a queue from request_type and destination_layer, validates that a route exists, serializes the Pydantic payload to JSON and sends SQS attributes for processing_layer and request_type.
Sources: C:82-110, :210-243, :279-310.
Transport retry uses AsyncRetrying on ClientError and the configured transient network exception classes, with exponential waits and the configured attempt budget. After exhaustion it raises SendMessageException.

5. Batch helper is a DB batch plus sequential individual sends

batch_send_msgs_to_target_queue:
- Returns empty result for no payloads.
- Validates all payloads first.
- Generates a new msg_tracking_id and tracking row for every payload.
- Flushes and commits ALL tracking rows in one DB transaction.
- Sends payloads one by one by calling client.send_message, collecting succeeded/failed tracking IDs and exceptions.
- Best-effort updates native IDs for successes, stamps failed rows separately.
- If every send fails, raises SQSException; with mixed results it returns BatchSendResult.
Sources: H:436-582.

It is not an AWS SendMessageBatch call. It does not perform the single helper's IntegrityError row recovery. The docstring's "2 DB sessions total" is an approximation: failure stamping can add another session.
Sources: H:444-446, :487-515, :518-545, :547-572.

Caller handling:
- Feeds restores failed feed schedules after a partial result, or all schedules after an exception, then a later tick can retry. It maps failed tracking IDs back to feed IDs.
src/microservices/feeds/services/feeds.py:271-315.
- WebEx L1 builds per-article L2 payloads, calls the batch helper, logs partial failure and marks its L1 activity completed; the log explicitly delegates failed sends to a later feed run.
src/microservices/web_extraction/services/web_extraction.py:588-627.
This means the later feed schedule and caller guards are part of the recovery story; the batch helper alone is not a delivery guarantee.

6. Confirmed source-level limits and failure windows

A. Committed tracking row, process stops before send.
The single helper intentionally recognizes this as UNKNOWN on retry (native ID NULL, no failure timestamp) and sends using the same tracking identity.
H:212-217 documents and implements this.
However caller guards can prevent the helper from being reached, as detailed below.

B. SQS accepted, process stops before native-ID update.
A later helper invocation sees UNKNOWN and may resend with the same application tracking ID. This favors recovery over false success, but allows duplicate deliveries. Downstream idempotency is required.
Sources: H:377-421; receiver uniqueness example above.

C. A send raises after SQS may have accepted it.
Best-effort failure state means retry is allowed; it is not proof the broker never accepted the first message. Same duplicate possibility.
Sources: H:391-395; C:245-262.

D. Native-ID update is auditing, not a durable send transaction.
Missing/unparseable native ID or failed update does not fail the helper. No background resend scanner is invoked by this helper itself.
Sources: H:397-421.

E. Retried payload versus stored tracking body.
On conflict, only the payload's msg_tracking_id is overwritten with the old value; the helper does not compare or update the existing message_body before resending the current payload. Therefore exact stored-body equality across a retry depends on caller determinism, not a check in this helper.
Sources: H:192-236, :352-362, :379-383.
This is a source-level limit, not evidence that any real retry changed its business payload.

F. Concurrent sends are not fenced around the external call.
After existing-row lookup the helper holds no row lock spanning SQS I/O. Two concurrent recovery invocations could both see UNKNOWN and send the same application ID. Consumer idempotency, not a cross-system transaction, handles that class of duplicate.
Sources: H:149-154, :327-377.

8. Invented example: one article, one source activity, one handoff

3. Activity creation and the state machine are application rules

create_activity_row:
- chooses service-specific required inputs, e.g. feed_id for WebEx L1, doc_id for L3, source/activity/type discriminator for AIQ L1;
- creates QUEUED, stamps queued_at, flushes and commits even when passed a caller's session;
- wraps any PostgreSQL 23505 unique violation as DuplicateActivityException.

The last detail matters: it does not inspect which unique constraint failed before labeling the error a duplicate. AIQ L1 and EC L1 have unique source_activity_id as well as msg_tracking_id. Simply issuing a new tracking UUID against the same upstream source is not a general replay mechanism.

4. Duplicate resolution and retry claim

register_activity performs the initial duplicate read and activity create in one session. On a uniqueness race it attempts to delete that received message and returns no work. On an existing row it closes the lookup session before resolve_duplicate.
Source: src/common/utils/activity_registration.py:68.

resolve_duplicate decisions:
- COMPLETED/DUPLICATE/SKIPPED: delete the received message; a deletion failure is logged and the message may reappear.
- FAILED: attempt reclaim.
- QUEUED: reclaim only if queued_at exists and is older than the supplied threshold.
- PROCESSING: always consult the atomic claim; the SQL predicate decides whether it is stale.
- Other/fresh/unclaimed: leave on queue for visibility timeout/redelivery.
Source: src/common/utils/duplicate_message.py:145.

try_claim_activity_retry performs one conditional UPDATE and checks rowcount == 1. Its predicate requires completion_at IS NULL, then either QUEUED/FAILED, or PROCESSING with a missing/old process_started_at. It writes PROCESSING and a fresh process_started_at and commits.
Source: src/common/helpers/activity.py:567 and :602.

This is not a heartbeat/liveness probe: another process can still be running after the configured stale age. A successful claim is evidence that the SQL condition won, not proof that external side effects never occurred in the earlier attempt. Idempotent downstream writes still matter.

5. Timeouts, cancellation, queue visibility and reaping are separate mechanisms

AIQ task handler first commits PROCESSING, calls the pipeline, catches CancelledError separately, records activity failure best effort and re-raises cancellation. Ordinary exceptions use handle_error_state_update, then attempt guarded manual-document failure propagation.
Source: src/microservices/ai_questionnaire/tasks/message_processing/layer_one_messages.py:55.

handle_cancellation_state_update and handle_timeout_state_update open fresh sessions and use compare-and-swap PROCESSING -> FAILED. A completed activity is not clobbered by those two helpers. They do not update Accelerate's document status.
Source: src/common/helpers/activity.py:356 and :417.

handle_error_state_update differs: it uses the unconditional state updater. It skips missing activities and a SQLAlchemy pool timeout found within five __cause__ links, avoiding another blocked connection attempt. Cleanup is best effort.
Source: src/common/helpers/activity.py:490 and :547.

InflightTaskManager wraps the coroutine in asyncio.timeout, emits one canonical timeout error, calls the registered timeout cleanup callback and releases its slot. Shutdown can drain, then cancels remaining tasks and gathers them. An asynchronous task completion log is not equivalent to all downstream stages completing.
Source: src/common/utils/inflight_tasks.py:142 and :266.

The shared worker validates/registers BEFORE awaiting a free task slot. Queue visibility began at receive, not at task start; slot pressure and registration latency consume the budget. Keep receive_count, task/queue timeout configuration and stale-handle errors when diagnosing a slow message.
Source: src/common/aws/sqs/worker.py:275-324.

AIQ successful processing is followed by delete_message. An exception adjusts visibility rather than deleting the message. Only explicitly retryable errors receive jittered exponential delay; false or unclassified errors get visibility zero, accelerating normal queue redrive. Cancellation re-raises and leaves the message.

Code defaults (not observed effective runtime): AIQ visibility 450s; task timeout derives as visibility minus 30s when unset; common stale-processing threshold 500s, stale-reaper threshold 900s, reaper interval 300s. Configuration can override them; verify effective values before interpreting age.

Its SQL compares timestamps with '< cutoff'; NULL timestamps do not satisfy that expression. Retry claiming handles a missing PROCESSING timestamp, but this reaper does not.

6. Commit-before-send: precise guarantee and current caller gaps

The sender writes application identity and payload into sent_sqs_messages and commits BEFORE queue I/O. This allows the next service's activity FK to resolve. The broker receipt is written afterwards in a separate best-effort transaction.
Sources: src/common/helpers/sqs_msg_delivery.py:327, :377, :397.

The single-send helper skips only when native_sqs_message_id is non-null AND send_failed_at is null. UNKNOWN (both null) and failed rows are candidates to resend, reusing the existing application ID after a matching uniqueness conflict. A lost broker response can still cause duplicate delivery; the database and SQS are not one transaction.
Source: src/common/helpers/sqs_msg_delivery.py:191-236.

Not every producer has a unique activity key: WebEx L1 fans out and feeds have no equivalent single-activity uniqueness. Batch sending commits all tracking rows, then sends individually. See queue-delivery-detail.txt for exact producer keys, failure windows and tests.

Two independently source-checked caller gaps:

The idempotency document describes article replay from AIQ L1 with new activity history and reused article/document content. Do not turn that prose into an invented replay command. This review did not establish a general article replay CLI or a safe new-source identity policy. Unique source_activity_id must be respected. Event Synthesis has a separate, explicit replay mechanism below.

- ActivityArticleStatus records a finished L3 outcome. DUPLICATE short-circuits; canonical article_id excludes its own old chunks from duplicate detection.

10. Transaction tools: their names do not enforce read-only behavior

AsyncDatabaseSessionManager.session yields a session, rolls back ordinary exceptions and always closes. It does NOT commit a successful block.
read_session/write_session both use _commit_scope: commit on normal exit, ordinary error propagates through rollback/close. read_session is an intent label, not a database read-only restriction.
Source: src/db/session_manager_async.py:190, :219, :234, :249.

expire_on_commit=False allows loaded scalar attributes after commit. It does not make unloaded lazy relationships safe outside the scope. Pinned sessions keep one physical connection for session-level advisory locks, but the caller must still commit normal read transactions before external I/O.

2. Zero, missing and invalid are different outcomes

Missing doc_article_map: mark the extraction activity SKIPPED and return no raw-event IDs.
Valid response with zero events: mark activity COMPLETED and return no raw-event IDs.
Malformed/invalid response: retry only the declared invalid-response exception within the LLM parsing loop. Repaired JSON is rejected rather than accepted as a possibly truncated extraction. Transient provider/API errors propagate to the queue-level failure path.
These three branches must not be collapsed into “no events were extracted.”

4. Fan-out from one extraction to many synthesis messages

publish_raw_events creates one notification per raw_event_id. It commits EventExtractionSentSQSMessage rows before external queue sends, then separately stamps native queue IDs or send_failed_at.
The payload has raw_event_id, integer doc_id, activity_trail, published_at and optional replay_reason, plus the common tracking identity. The source publishes one global FIFO message group, with raw_event_id as the queue deduplication key.
Sources: services/helpers/raw_event_publisher.py:32,47,85,99,111; src/microservices/event_synthesis/aws/sqs/messages.py:18.

This publisher intentionally differs from the shared one-message helper because one extraction activity has N output events. Its pending query selects only rows with neither native ID nor send_failed_at; prior failed rows are not automatically retried by that selection. 5. The synthesis worker has a separate ledger

- completed ledger: acknowledge without running synthesis again;

6. Deciding whether this is a new event or more evidence for an old one

SynthesisOrchestrator.process_one resolves tenant ownership from the document, prepares the incoming summary embedding outside write transactions and retrieves candidates on the Accelerate writer. A stale replica miss could create a duplicate event.

CandidateRepository combines entity-overlap, taxonomy/time and embedding channels, hydrates scoring inputs, deduplicates and ranks the combined candidates. Source defaults: per-channel limits100, final limit150, active events only. Date-window defaults differ by channel; an unknown date uses recent last_article_on. Sources: repositories/candidates.py:59,180,278,645; config/candidate_retrieval.py:12.

The match score is NOT a probability. It is a weighted similarity:
sum(weight * available factor) / sum(available weights).
A factor returning None is excluded. A measured0 remains evidence against.
Default weights are entity0.25, type0.25, category0.15, temporal0.15, summary0.20. Thresholds are required config values; this review did not inspect live settings.
Sources: services/scoring/composite.py:49; services/scoring/match_config.py:12.

Factor meanings:
- Entity: Jaccard overlap using complete entity sets. Both empty -> unavailable; one empty ->0.
- Type:1 for same type,0.35 for different types in the same known category,0 otherwise; unknown type -> unavailable.
- Category:1 for same known category,0 otherwise; unknown -> unavailable.
- Time: coarsest precision wins. Exact/day tier decreases by distance; month/year precision uses coarser bands.
- Summary: precomputed cosine similarity clamped to[0,1], or unavailable.
Source: services/scoring/factors.py:26,48,69,82,134.

Synthetic arithmetic only: factors0.8,1,1,0.8,0.9 with default weights produce0.90. That does not on its own authorize a merge: the configured thresholds and guards also apply.

No entity overlap and a different type force CREATE_NEW. No entity overlap with matching type cannot auto-merge. An automatic merge also requires a measured summary at the configured minimum (source default0.75). Comparisons use unrounded values; stored diagnostics are rounded.
